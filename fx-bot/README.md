# fxbot — FX自動売買フレームワーク

バックテスト・ペーパートレード・実弾稼働を、**同じ戦略コード**で回すためのフレームワークです。
本体は標準ライブラリのみで動きます（追加インストール不要）。

---

## ⚠️ 最初に: SBI証券について

**SBI証券は個人向けのFX取引APIを提供していません。**

日本国内でAPI経由の自動売買が公式に可能なのは、次のような業者です。

| 業者 | 提供API | 対象 |
|------|---------|------|
| OANDA証券 | v20 REST / MT4・MT5 | FX |
| auカブコム証券 | kabuステーションAPI | 株式・先物（FX不可） |
| MT4/MT5対応業者 | MQL4/MQL5 EA | FX |

したがって「SBI証券で自動売買」を実現する手段は、**ブラウザの画面自動操作（スクレイピング）しかありません**。
これには次のリスクがあります。

1. **規約リスク** — 証券会社の利用規約は一般に、機械的な自動アクセスを禁止・制限しています。違反すると口座凍結や強制解約の可能性があります。
2. **技術リスク** — 画面構成（DOM）は予告なく変わります。セレクタが1つ外れただけで「発注したつもりが出ていない」「決済したつもりが建玉が残る」といった、**資金を直接失う形の故障**が起きます。
3. **認証リスク** — デバイス認証やワンタイムパスワードが挟まると、無人での連続稼働は成立しません。

このため本リポジトリの `fxbot/brokers/sbi_web.py` は、**動く実装ではなく安全側に倒した雛形**です。

- 既定で `dry_run=True`（発注内容をログに出すだけで、実際には何も送らない）
- 実発注には `dry_run=False` **かつ** `confirm_live_trading=True` の両方が必要
- セレクタはハードコードせず設定ファイルから与える（未設定なら実発注モードで起動を拒否）
- 認証情報は環境変数からのみ読む

**推奨**: まず `paper` モードとバックテストで戦略を固め、実弾はOANDAのデモ口座（`practice`）→ 少額の本番、という順で進めてください。

## クイックスタート

```bash
cd fx-bot

# 1) 動作確認（合成データでバックテスト）
python3 -m fxbot backtest --bars 3000

# 2) 実データを取得（OANDAのトークンがある場合）
export OANDA_TOKEN=xxxx
export OANDA_ACCOUNT_ID=101-xxx-xxxxxxx-xxx
python3 -m fxbot fetch --symbol USD/JPY --granularity H1 --bars 5000 --out data/usdjpy_h1.csv

# 3) 実データで検証
python3 -m fxbot backtest --csv data/usdjpy_h1.csv --strategy breakout --trades 20

# 4) パラメータ探索
python3 -m fxbot optimize --csv data/usdjpy_h1.csv --strategy breakout \
  --param entry_period=10,20,30,40 --param exit_period=5,10,20

# 5) ペーパートレード（実弾ゼロで稼働）
#    価格は次の優先順で決まる:
#      --csv があればその足を再生 / 設定の broker が実業者ならその気配値 / 無ければ合成データ
python3 -m fxbot paper --config examples/config.json --csv data/usdjpy_h1.csv

# 6) 実弾（デモ口座で十分検証してから）
python3 -m fxbot live --config examples/oanda_live.json --i-understand-the-risks
```

テスト:

```bash
pip install pytest
python3 -m pytest -q      # 140件
```

## 構成

```
fxbot/
  models.py        通貨ペア・足・注文・建玉・トレードの定義
  indicators.py    SMA/EMA/RSI/ATR/ボリンジャー/MACD など
  strategies/
    base.py          戦略の基底クラス（warmup管理）
    sma_cross.py     移動平均クロス＋トレンドフィルタ
    rsi_reversion.py RSI逆張り
    breakout.py      ドンチャン・ブレイクアウト
  risk.py          ★ポジションサイズ計算と各種停止条件
  brokers/
    base.py          ブローカー抽象
    paper.py         ペーパー/バックテスト用（スプレッド・スリッページ模擬）
    oanda.py         OANDA v20 REST（実働）
    sbi_web.py       SBI画面自動操作（雛形・既定で無効）
  feeds.py         CSV読み込み・合成データ生成
  pricesource.py   ペーパー稼働時の価格供給（実業者の気配値 / 保存済み足の再生）
  backtest.py      検証エンジンと成績指標
  engine.py        リアルタイム稼働ループ
  journal.py       取引記録（CSV + JSONL）
  config.py        設定ファイル読み込み
  cli.py           コマンドライン
```

戦略は `Strategy` を継承して `warmup` と `on_candle()` を実装するだけで追加できます。
`strategies/__init__.py` の `REGISTRY` に登録すれば、設定ファイルから名前で呼べます。

## リスク管理（このフレームワークの中心）

自動売買で口座を失う原因は、戦略の優位性が無いことよりも**リスク管理の不在**であることが多いです。
`risk.py` は戦略が何を言おうと、次を満たさない注文を通しません。

**ポジションサイズ** — 1トレードの損失額を口座の一定割合に固定します。

```
数量 = (資金 × risk_per_trade) ÷ (損切り幅 × 円換算レート)
```

資金100万円・リスク1%・損切り50pipsなら、2万通貨（損切りに掛かると1万円 = 1%の損失）。
損切りが狭いほど数量は増えるので、レバレッジ上限が先に効いて削られることがあります。

**取引を止める条件**

| 設定 | 既定 | 動作 |
|------|------|------|
| `daily_loss_limit` | 3% | 当日の損失が到達したら停止（翌日自動再開） |
| `max_drawdown` | 20% | 資産ピークから下落したら停止（**手動解除が必要**） |
| `max_consecutive_losses` | 5 | 連敗数が到達したら停止（手動解除が必要） |
| `max_leverage` | 5倍 | 実効レバレッジの自主上限（法定は25倍） |
| `max_spread_pips` | 3.0 | スプレッド拡大時は発注しない |
| `trading_hours` | 全時間 | UTC時間帯フィルタ |
| `trade_on_weekend` | false | 土日は発注しない |

**その他の拒否条件** — 損切り価格が建値の誤った側にある / 損切り幅が狭すぎ・広すぎ / 必要数量が最小取引単位未満 / 建玉数が上限。

バックテスト結果の末尾には「途中停止」と「見送り回数」が表示されるので、リスク管理が
どこで効いたか確認できます。

## バックテストの前提（数字を信じすぎないために）

- 判断は**確定した足の終値**で行い、約定も同じ終値ベース。実際には終値で必ず約定できるとは限りません。
- 1本の中で損切りと利確の両方に触れた場合、**損切りが先**とみなします（足データからは順序が分からないため、保守側に倒しています）。
- 買いはAsk、売りはBidで約定し、さらにスリッページを不利方向に乗せます。損切りにも窓開けを想定したスリッページが乗ります。
- スワップ（金利差）は日数按分の簡易計算です。長期保有戦略では実額と乖離します。
- **合成データ（`--bars` 指定時）の成績には何の意味もありません。** 配管の動作確認用です。実相場の性質（窓、ニュースによる急変、ボラティリティのクラスタリング）を持ちません。
- `optimize` で見つかる「最良パラメータ」は、その期間に最も都合よく当てはまった値です。必ず別期間（アウトオブサンプル）で再検証してください。

成績指標は「トレード損益の合計 = 残高の増減」が常に一致するようテストで担保しています。

また、**損切り・利確による決済（＝実運用で最も多い決済経路）は、こちらが決済を指示したわけでは
ないため、明示的に回収する必要があります。** `Broker.poll_closed_trades()` がその経路で、
エンジンが毎ティック回収してリスク管理の連敗カウントと取引記録へ流します。
独自のブローカーアダプタを書く場合は、これを実装しないと損切りが「無かったこと」になります。

## 設定ファイル

JSON（標準）またはYAML（PyYAML導入時）。`_` で始まるキーは注記として無視されます。
サンプルは `examples/` にあります。

**認証情報は設定ファイルに書けません。** `password` / `token` / `secret` などを含むキーに値を直書きすると、
読み込み時にエラーになります。環境変数で渡し、ファイルには環境変数名（`password_env` など）だけを書いてください。

```bash
export OANDA_TOKEN=xxxx
export OANDA_ACCOUNT_ID=101-xxx
# SBIアダプタを使う場合
export SBI_USERNAME=xxxx
export SBI_PASSWORD=xxxx
export SBI_TRADE_PASSWORD=xxxx
```

## SBIアダプタを自分で完成させる場合

`fxbot/brokers/sbi_web.py` の `_TODO_` が付いたメソッド（`_login` / `get_tick` /
`get_positions` / `place_order` / `close_position`）を実装します。実装時の必須事項:

1. **発注後に必ず約定確認をする。** 注文受付画面や約定履歴を読み、実際に通ったことを確認できない場合は**リトライせずエラーで止める**。二重発注は最も速く資金を失うバグです。
2. **決済後は建玉一覧を読み直す。** 当該建玉が消えたことを確認するまで成功扱いにしない。
3. **建玉はローカル変数ではなく画面を正とする。** 手動決済やロスカットでズレます。
4. **数量の単位を画面表記と突き合わせる。** 通貨単位か万通貨か（SBI証券FXαは1万通貨単位）。`instrument_overrides` で `min_units` を設定してください。
5. **価格の健全性チェックを入れる。** 桁を1つ読み違えると、リスク計算がすべて壊れます。
6. **追加認証が出たら黙って続行しない。**

`screenshot_dir` を設定しておくと、失敗時に画面が保存されて原因調査ができます。
